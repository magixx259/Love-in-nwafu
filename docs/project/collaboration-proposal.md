## 交接规则

1. **一个文件一个主维护方。** 其他方可以读取、提出修改建议；不要同时改同一份人物卡或同一个剧情脚本。
2. **剧情交付写清状态。** 给程序方具体文件、场景顺序、已确认对白、未定占位、是否替换旧开场。程序遇到冲突先记录差异，不把全部草稿自动变成正式设定。
3. **美术交付写清版本。** 列出角色、服装、表情、文件路径、像素尺寸、透明背景情况、用户认可范围和使用许可。旧版本保留，不能因为版本号更大就自动替换已认可版本。
4. **程序交付附实际检查结果。** 至少说明能否启动、能否走完目标流程、存读档是否检查、未开放入口是否处理；未测项明确标注。不要只用提交成功代表游戏可玩。
5. **当前共用目录时，建议只有 DeepSeek 负责 Git 暂存、提交、推送和打包。** 其他方完成文件后列出改动清单，交由它核对；提交前检查清单与差异，不使用会夹带他人未完成内容的全目录暂存。这一角色安排仍需各方采用后才生效。
6. **并行规模增大后使用独立工作副本。** 不同文件夹与分支分别编辑，完成后再合并。单纯在同一个目录来回切分支不能隔离其他正在写文件的进程。
7. **保持状态同步。** 策划维护设定与待定事项；程序维护当前版本、运行方式和测试结果；美术维护当前认可基准。交接时同时指出哪些旧描述已过期。
